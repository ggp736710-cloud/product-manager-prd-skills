# 产品方案设计

基于需求分析设计可评审的产品方案。重点是用户能力、流程、规则、范围和决策；技术架构与实现细节只有在有项目依据或用户要求时才定稿。

## 执行约定

- 先读取需求分析及相关项目资料；保留需求、场景和范围 ID，逐项关联方案。
- 区分已知事实、方案建议、假设、待研发确认和待业务确认。不得臆造技术栈、系统能力、性能数据、成本或团队经验。
- 先判断方案适用复杂度：小型功能不强制输出完整架构、ERD 或多方案打分；只生成解决问题所需的设计。
- 有多个可行方案时，对比用户价值、成本/复杂度、风险、依赖和可逆性；没有证据的维度标记未知，不做伪精确评分。说明推荐方案及放弃其他方案的原因。
- 如关键缺口会导致方案分叉，提出少量针对性问题；否则列为待确认，继续形成可评审草案。

## 工作步骤

1. 核对需求目标、范围、场景、约束和开放问题；发现冲突时列出，不自行裁决。
2. 将用户目标映射为功能/能力及模块职责，描述输入、输出、依赖和角色权限。
3. 梳理正常、边界、失败、取消/撤销等关键交互流程与状态变化。按需使用 Mermaid。
4. 明确产品规则、数据概念与关键字段；涉及系统接口、数据库或技术架构时，区分产品约束和需研发确认的实现设计。
5. 对有依据的候选方案进行比较并记录决策；标明决策人/状态（建议、已确认、待确认）。
6. 列出风险及触发条件、影响、处置建议、责任方/待定责任方和验证方式。
7. 检查需求覆盖、未覆盖项、范围新增项及开放问题，形成供 PRD 阶段引用的方案。

## 默认输出

```markdown
# [需求名称] 产品方案
## 设计摘要与决策状态
## 需求覆盖映射（需求/场景 ID → 能力/流程）
## 角色、权限与功能范围
## 用户流程与关键状态
## 产品规则与数据概念
## 方案选项与决策记录（适用时）
## 依赖、集成边界与待研发确认项
## 风险、触发条件与应对
## 未覆盖需求、假设及待确认问题
```

图表只在能减少歧义时使用。按用户指定格式和路径交付；默认先在回复中提供方案。

## 阶段衔接

进入规格生成时提供已确认方案、需求/场景 ID 映射、规则、状态、权限边界、风险以及未决问题。未确认的技术建议不得写成产品承诺。
